# Backend-driven UI languages

Date: 2026-11-20. Owner decision: English is the source, every other UI language is
defined by the backend. Arabic is removed from the product. Spanish (`es`) is the
first backend-defined language. Full contract: `docs/i18n_contract.md`.

## One process, three apps

Platform Admin, Workshop Admin and Technician share the same catalog layout, the
same endpoints and the same Flutter package (`client/packages/l10n`). No app keeps
its own manifest, bundle, language list or selection state.

```
GET /api/v1/i18n/ui-messages/{client}/manifest
GET /api/v1/i18n/ui-messages/{client}/bundle?lang=es
```

`client` is `platform_admin`, `workshop_admin` or `technician`. Responses carry
`catalogs` (namespaced `common` + client) and a flat merged `messages` map with
per-key English fallback, and `Cache-Control: no-store` because catalogs are
edited at runtime.

## Catalogs

```
server/src/main/resources/i18n/
  languages.json          single language registry (en, es)
  schema.json             placeholder/plural metadata for the 1,237 keys
  common/en.json          59 platform-common keys (dotted namespace)
  platform_admin/en.json  753 platform-only keys
  workshop_admin/en.json  1,237 keys
  technician/en.json      1,237 keys (identical to workshop_admin)
  workshop_admin/es.json  62 Spanish entries
  technician/es.json      62 Spanish entries (identical)
```

Adding a language = add an entry to `languages.json` and drop
`i18n/<scope>/<code>.json` files. No Flutter rebuild is required; the selector and
the UI follow on the next manifest fetch.

## Client

- `UiMessageApi.forClient(...)`, `languageSelectionProvider(client)`,
  `BackendLanguageSelector`, `UiMessageBootstrap` live in `package:l10n`.
- Workshop Admin and Technician render the shared selector (Settings, Profile).
- Platform Admin drives the same controller from its own header and sign-in
  switchers, so the data layer is shared while the presentation stays bespoke.
- No ARB ships with Flutter and no accessor is generated. Every string is
  addressed by `UiMessageKey` (one of the four typed key classes generated by
  `dart run tool/generate_ui_keys.dart`) and resolved through `UiStrings` /
  `UiStringsScope` from the backend bundle with no English fallback literal.
- `i18n/schema.json` is the key-union and placeholder/plural source for that key
  generator and must stay identical to both client catalogs (enforced by
  `ui_keys_parity_test.dart`).

## Verified behaviour

- Manifest/registry for all three clients, `no-store`, 404 for unknown client/lang.
- Live browser (Playwright MCP, workshop build at :5302): Settings shows English +
  Español from the manifest; selecting Español renders "Ajustes / Idioma / Cerrar
  sesión / Trabajos" without a rebuild.
- Removing `es` from `languages.json` + parking the `es.json` files and reloading:
  the language card disappears and the UI is English only. Restoring the files and
  reloading: Español returns. Both cycles were confirmed in the browser.

## Removed

- `app_en.arb`, `l10n.yaml`, `flutter gen-l10n`, `tools/apply_remote_english.mjs`,
  generated Arabic localization, `languageArabic`, the sign-in AR toggle, `isArabic`
  theme/token/RTL branches, Arabic showroom variants.
- The generated Dart accessor itself: `lib/l10n/gen/app_localizations*.dart`,
  `tool/generate_localizations.dart` and its generator-only tests. Apps now use
  `UiStrings` with the key classes; `schema.json` and `generate_ui_keys.dart` stay.
- `server/src/main/resources/i18n/{messages,report,delivery}_ar.properties` and the
  hardcoded `"ar"` branches in report, delivery, document and master-content code.
- Flyway migrations `V102/V120/V124` are applied history and were not touched; the
  generic translation-overlay tables remain for future languages.
