## New findings

### N8 — MAJOR — the consent-blocked card drops the reason and the checklist link

The large-text switch makes the card list the required layout at every width, including 1440/1024 2x. JobsQueueCards._footer handles JobPrimaryAction.none with one inline note, jobsPublicationBlocked, and nothing else (lib/src/features/jobs/queue/jobs_queue_cards.dart:198-210); for APPROVED without consent the policy returns none (shared/job_actions.dart:114-124). Brief §5 requires "Publication blocked" with the reason and the same checklist link, and §6 says the card action is the same policy table; docs/briefs/brief-jobs-j1b-queue.md:60-63 repeats it. The detail (N2) and the wide inspector comply, so the card is now the only surface missing it — and the only surface at 2x desktop widths. The queue fixture never exercises it: _job defaults consentGranted: true (test/jobs_queue_test.dart:106), and the 2x captures stop before the Approved (1) card, so no test or screenshot catches it. This is the regression introduced by routing desktop large text through cards.

**Fix:** in the none branch, render jobsPublicationBlocked + jobsPublicationBlockedBody + a secondary View checklist button (Key job-card-publish-checklist-<id>) that opens PublishChecklistPage; add a queue fixture with APPROVED/no-consent and tests at 390 and 1440/2x that tap the link and assert PublishChecklistPage; add the card capture.
**Owner:** jobs_queue_cards.dart + the queue test/capture author.

### N9 — MINOR — the conflict view repeats the refresh control

detail_conflict_1280.png shows two explicit Refresh buttons: the banner's secondary Refresh (detail/job_detail_states.dart:107-113) and the sticky primary Refresh added by the N7 fix (detail/job_detail_action_bar.dart:151-162); the top bar also has its refresh icon. The N7 behavior is correct, but the banner button is now redundant and competes with the primary for the same action.

**Fix:** make the conflict banner message-only (keep liveRegion and the warning tone), leaving one explicit Refresh control; keep the top-bar icon as the standard affordance. Update the conflict capture.
**Owner:** detail/job_detail_states.dart / job_detail_action_bar.dart.

### N10 — MAJOR (residual, exposed by this review) — the wide inspector's blocked state has no "Open job"

jobs_inspector.dart:321-340 renders the blocked reason and the checklist, but jobs_inspector.dart:341-375 renders the text Open job and the More menu only inside if (primary != null). For APPROVED without consent the policy primary is none (job_actions.dart:114-124), so a selected job at ≥1100 shows the checklist button and no route to JobDetailPage; tapping a table row only selects. Brief §5's inspector footer is "one primary action + a text Open job", and §3's "Open the full record" flow depends on it. The phone card body still opens the detail, but the wide inspector in this state is a dead end. No queue test covers it (the fixture's Approved job has consent).

**Fix:** render _OpenJobLink (and the More menu) outside the primary != null branch, or add a blocked-state footer row with Open job; add a test with an APPROVED/no-consent row at 1280 that taps job-detail-open and expects JobDetailPage, plus a queue_consent_blocked_1280.png capture.
**Owner:** jobs_inspector.dart footer + test.
